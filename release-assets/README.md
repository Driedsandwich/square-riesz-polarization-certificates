# Release assets

## v1.0.2

Three assets, in two roles:

| Asset | Role |
| --- | --- |
| `square-riesz-polarization-certificates-v1.0.2.zip` | canonical distribution |
| `square-riesz-polarization-certificates-v1.0.2.zip.sha256` | canonical distribution |
| `square-riesz-polarization-certificates-v1.0.2.publication-attestation.json` | publication integrity |

Whether these assets exist is answered by the GitHub Release, not by this file:
if GitHub reports the `v1.0.2` Release as published and immutable with these
assets attached, they are the assets for `v1.0.2`; otherwise the `v1.0.1` assets
below remain the latest canonical ones.

The distribution digests and sizes are recorded in the publication-attestation
asset and in GitHub's Release asset metadata, and can be confirmed by
downloading the assets and checking the ZIP against its `.sha256` companion.
They are deliberately not written here: this file is inside the archive it would
be describing, so it cannot state that archive's digest.

The ZIP and its companion are generated by `scripts/build_release_assets.py`
from the exact tag target, uploaded to a draft Release, downloaded again from
that draft, and checksum-verified. The attestation asset is then generated by
`scripts/build_publication_attestation.py` from those measurements and uploaded
to the same draft, so that publication freezes all three together.

The builder that produces the ZIP must be the builder inside the commit it
archives: it reads `scripts/build_release_assets.py` out of the target tree,
hashes those bytes against the bytes of the file it is running from, and refuses
if they differ. Because a `v*` tag cannot be moved after it is created, the
tagged build is also required to reproduce a digest measured by an earlier build
of the same commit made before the tag existed.

The attestation asset carries the builder's machine-written `build-record.json`
in full, together with the `build_record_sha256` of that record, so the digest
published in the asset can be recomputed from the object published beside it.

Both generators treat the whole span from the `os.rename` / `os.replace` call to
the command's return as one publication transaction — the statement that records
the syscall, and the success report after it, are both after the output exists —
and decide what happened by looking at the filesystem rather than by trusting a
flag that an interruption may have skipped. `SIGKILL`, a crash and a power loss
remain outside what any handler can catch.

The draft is counted at two points. Before the attestation is generated it must
hold exactly the two distribution assets, with distinct ids and nothing else;
that measured inventory is an input the generator refuses to proceed without.
After the attestation is uploaded and before publication it must hold exactly
those two plus the attestation. The second count is not inside the attestation,
because a file cannot state the contents of a release it has not yet joined.

The attestation asset is a release asset rather than release-body text because
GitHub's immutable releases protect the tag and the assets, while the title and
notes remain editable after publication. GitHub's generated Release attestation
binds the tag, the release commit and all three assets.

The existing `v1.0.0` and `v1.0.1` assets are not modified by `v1.0.2`.

## Interpretation

Canonical ZIPs are generated outside the repository tree to avoid recursive packaging. GitHub's automatically generated “Source code” archives are convenience downloads and are not the canonical deterministic Release assets.
