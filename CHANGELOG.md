# Changelog

## Unreleased

## 1.0.2 — 2026-08-08

### Corrected

- Correct the `rigorous_upper_witness` decimal in 18 of the 44 rows of `data/certified-results.csv` and `data/certified-results.json`, and the `interval_width` that follows from it. Those decimals had been rounded to nearest, which placed them below the exact potential at the upper witness point and therefore below a valid upper bound; they are now rounded outward. Each correction is `+1` in the final published digit. The fixed configurations, the certified lower bounds, the upper witness points, the two certifier families and the stored replay evidence are unchanged. See `docs/errata-v1.0.1.md`.

- Correct the `symmetry_or_family` prose of `n=15` and `n=16`, which described exact symmetries the published finite decimals do not have. The field is non-normative provenance prose and no bound depends on it; the exact invariance of all 44 configurations under the eight symmetries of the square is now computable with `certificate_lib.exact_square_symmetries`. See `docs/errata-v1.0.1.md`, which separates this clarification from the arithmetic correction above.

### Added

- `scripts/certificate_lib.py`: exact-rational helpers and fail-closed AST extraction of certifier constants. The certifier sources are never imported, executed, `eval`-ed or `runpy`-ed by the checking tools.
- A static entry-point check: each certifier must have exactly one `__main__` guard with no `else`, whose body is exactly `main()`, exactly one `main()`, one direct `certify()` call inside it, and the four final assertions over the certified result, the minimum leaf bound and the witness value. The allowed shape was derived from an inventory of the existing 88 certifiers. This rejects a module that prints `status: CERTIFIED` from its guard without running the proof — which the exit-code and status checks alone would have accepted.
- `certificate_lib.validate_proof_output`: one proof-output contract, shared by `verify_one.py`, `verify_all.py`, `validate_replay_output.py` and the historical and saved-replay checks. A successful run must carry exactly one `status`, `target_decimal`, `splits`, `leaf_count`, `maximum_depth` and `minimum_leaf_lower_bound_decimal` line and one upper witness value line; the target must equal the certifier `TARGET` as an exact rational, the counts must be canonical non-negative integers with at least one leaf, the minimum leaf bound must be at least the target, and the upper witness value must reproduce the exact potential at that certifier's witness point at that certifier's own printing precision. A stdout file whose entire content was `status: CERTIFIED` previously passed every exit-code, status, hash, schema and aggregate check in the replay pipeline.
- `scripts/check_frozen_corpus.py` and `data/frozen-corpus-v1.0.1.sha256`: the 531 files that carry the mathematics, pinned to the objects of `v1.0.1` (`d92992101ca45a5cd755b8d962652ab7e4329973`). `SHA256SUMS` is regenerated whenever the repository changes and therefore cannot distinguish a maintenance patch from an edit to a certifier — replacing a certifier with a proof-skipping version and updating the historical script hash, the per-job metadata, the aggregate tables and the manifest in the same change left the semantic check, the manifest verifier, the release check, the generator check, the upper-witness audit and `verify_one.py` all reporting success. Inside a Git repository the authority is the release commit, read **raw** with `git ls-tree` and `git cat-file`: the release blobs, the in-tree baseline and the working tree must all agree, so editing the baseline alongside the corpus fails. Object replacement is disabled on every read (`git --no-replace-objects`, `GIT_NO_REPLACE_OBJECTS=1`, `GIT_REPLACE_REF_BASE` dropped) and every `cat-file --batch` response is matched to the object id, type and size requested, because `git replace` otherwise serves substituted content under an unchanged commit or blob name; `refs/replace/` is enumerated and, under `--require-git-anchor`, its existence is a failure. The comparison covers file type and Git mode as well as content: the working tree is inventoried with `lstat`, so a frozen path replaced by a symlink to an identical copy, or given the executable bit, is rejected rather than read through. All 531 paths of `v1.0.1` are mode `100644`. Outside one — a release archive or an evidence snapshot — the run reports `git_anchor_unverifiable=1` rather than implying a comparison it did not make, and `--require-git-anchor` makes that a failure. See `docs/frozen-corpus.md`. It runs first in both workflows, with `fetch-depth: 0`.
- `validate_replay_output.py --expect-source-commit` and `--expect-source-clean`, used by the full-replay workflow. Local evidence comes from an uncommitted tree and is not required to be clean.
- An explicit unit-square check on every upper witness point, in the generator, the audit and the semantic consistency check. The potential at a point bounds the minimum over `[0,1]^2` only if the point is in `[0,1]^2`; nothing had checked it.
- `scripts/validate_replay_output.py`: re-derives a fresh replay's conclusion from its own files — recomputing each certifier's SHA-256, re-classifying each stdout/stderr pair, recomputing the aggregates, and requiring exactly the expected file inventory.
- A strict JSON loader that rejects duplicate object keys and `NaN`/`Infinity`, applied to the result tables, the metadata and both replay formats, plus exact field-set and type checks for the metadata and the stored replay records.
- `* -text` in `.gitattributes`. `SHA256SUMS` is verified against working-tree bytes, and a clone with `core.autocrlf` set would otherwise rewrite them; measured under `false`, `true` and `input`, with a control that proves the check can fail.
- `scripts/regenerate_certified_results.py`: the single deterministic generator for both result tables, with `--check` and `--write`. The tables are now build products, and no derived value can be hand-entered.
- `data/results-metadata.json`: the values that have no definition to compute — provenance prose, the externally submitted figure, the local-minima count, the descriptive minimum separation, and the presentation precision.
- `scripts/audit_upper_witness.py`: recomputes every upper witness value exactly and exits non-zero on any published decimal that falls below it.
- `scripts/check_semantic_consistency.py`: cross-checks the configuration set, CSV against JSON field by field as strings, the coordinate files against each other and against both certifiers, the certifier constants, the upper witness inequality, and the stored replay evidence including per-record script hashes and recomputed aggregates.
- `scripts/verifier_runner.py`: one shared success contract for the replay scripts.
- `tests/`: regression and mutation tests, including the n=15 case in both directions and single-point corruptions of the coordinates, the certifier constants, the tables and the replay evidence.
- `docs/data-schema.md` and `docs/errata-v1.0.1.md`.
- `scripts/build_release_assets.py` and `tests/test_release_assets.py`: the canonical release assets are now built by a script that lives in the tree it archives. The `v1.0.0` and `v1.0.1` assets were produced by one-shot workflows that deleted themselves in the release they published, so neither released tree contains the command that built it. The builder takes an exact 40-character commit, refuses a short, uppercase, non-commit or version-mismatched target, refuses a dirty tree, refuses an output directory that exists non-empty or lies inside the repository, disables Git object replacement on every read and refuses if `refs/replace/` is populated, and with `--require-tag` refuses unless the tag resolves to that commit. It then reads the archive back — CRC, one root prefix, no duplicate entries, no absolute or traversing paths, the archived `VERSION`, and the archive comment — unpacks it to a scratch directory and makes the archive verify its own `SHA256SUMS`, and writes a build record naming the target commit and tree, the tag, the Git version, the exact command, the entry count, the sizes and both digests. Which archive checks ran and which were absent from the archive are both recorded, so an absent check cannot be read as a passing one. `--require-tag` exists because the target is consequential: `git archive` writes the source commit id into the archive, so two commits with byte-identical trees produce archives with different digests, and the tag ruleset forbids moving a `v*` tag once it exists. Byte-identical output is asserted for repeated builds of the same commit with the same Git binary on one machine **with the subprocess environment constructed rather than inherited** — the tests measure it across three timezones; cross-platform and cross-version reproducibility is not claimed.

### Changed

- `scripts/verify_one.py` and `scripts/verify_all.py` now share one success contract: exit code 0, no timeout, exactly one `status: CERTIFIED` line on stdout, no status declared on stderr, and no structured failure token in either stream. The previous substring search accepted output that declared a status twice, declared none, or printed a bare `CERTIFIED` token, and ignored stderr entirely, so a run that printed a success on stdout and a failure on stderr and exited 0 counted as certified. The forbidden tokens were measured against all 88 certifiers first: none of their stdout contains one and all 88 stderr files are empty, so no existing run is reclassified.
- `scripts/verify_all.py --all` now requires the discovered configurations to equal the published set exactly, checked before anything runs, and reports missing and unexpected values separately. A directory set where `n52` was replaced by `n53` still yields 88 verifiers and previously passed.
- `scripts/verify_all.py --output-dir` now requires a directory that does not exist or is empty, and records `repo_relative_script` and `script_sha256` per job plus the expected key set, full Python version, platform, UTC timestamp and Git commit and dirty state in the summary.
- `check_semantic_consistency.py` checks the full replay CSV for header, column order, duplicate keys and the exact expected key set — duplicating one row and dropping another kept the row count at 88 and was previously accepted — checks stored stderr for contradicting statuses, and reports unexpected or missing files in the evidence directories.
- Both result tables are written through a temporary file and `os.replace`, so neither can be left partially written. The pair is still not atomic, which `docs/data-schema.md` states rather than implies.
- The `certifier_assertions_verified` counter is renamed `certifier_module_assertions_evaluated`: it counts the module-level and helper assertions the AST evaluator actually evaluated, and never covered the final assertions inside `main()`, which are now checked structurally and counted separately.
- `scripts/validate_replay_output.py` compares every `summary.csv` cell with the corresponding `summary.json` value through a shared renderer, field by field. Checking only the header, the row count and the key set accepted a row that claimed `certified=False` with a zeroed `script_sha256` while the JSON, the per-job files and the logs all said otherwise. It also fixes the summary and record schemas exactly: unknown fields, a bool in an integer field, a duplicated `expected_keys` pair, a non-UTC timestamp, a non-hex script digest, a `worker_count` below one and a non-canonical log name are all rejected.
- `check_semantic_consistency.py` binds each historical replay record to its own log. A record must name `logs/nNN_<method>.stdout.txt` and `...stderr.txt` exactly — not merely a file that exists — and its `status`, `splits` and `maximum_depth` must be the values in that log; the logged `target_decimal` is checked against the certifier `TARGET` and the logged upper bound against the exact potential at that configuration's witness point. Previously a record could point at another configuration's stdout and carry any split count at all, and remain consistent with the aggregate JSON, the per-job metadata, the aggregate CSV, the regenerated result tables and the manifest. Per-job metadata is now read with the strict JSON loader and its field set and types are fixed.
- `verify_all.py` reads the source tree's Git provenance **before** creating the output directory and running anything, and records it as `source_git_commit` / `source_git_dirty`. An output directory inside a repository is untracked, so the previous read — taken after the logs were written — reported a clean CI checkout as dirty.
- The entry-point check is now structural rather than a count of `certify()` calls anywhere inside `main()`. `main()` must open with `<name> = certify()` as a direct, argument-free call; its second statement must evaluate the potential at that certifier's own witness point; it must contain exactly two assignments and no `return`, `raise`, `try`, loop, `with`, lambda, nested definition, comprehension or walrus; its only `if` is the leaf-bound guard and its only loop is the coordinate listing, verbatim; every statement it evaluates for effect is a `print` from a fixed argument allow-list; its status line must be the proof's own verdict; and the four final assertions must be its last statements. `certify` and `main` must each be defined exactly once at module level and never rebound. Counting calls accepted `result = certify() if False else CertificateResult(True, ...)`, a module-level `certify = lambda: ...`, a shadowing second `def certify`, `print("status:", "CERTIFIED"); return` before the call, and `result = certify()` followed by `result = CertificateResult(True, ...)`; all five ran to exit code 0 printing `status: CERTIFIED`, four of them in under 0.03 seconds with `splits: 0` where the real certifier reports 3645.
- The historical and saved replay checks read the stored logs through the same proof-output contract as a live run. Setting `minimum_leaf_lower_bound_decimal` to `0` in a stored log and regenerating the manifest was accepted, and so was `splits: nonsense` with `maximum_depth: -1` once the same strings were written into the record, the per-job metadata, the aggregate CSV and the regenerated result tables. The four measurement columns of the result tables and the `splits` and `maximum_depth` fields of every replay record are now required to be canonical non-negative integers.
- `QUICK_NS` moved to `certificate_lib`, so the writer and the validator share one definition of what a quick replay covers.
- The test suite creates one real quick replay per process instead of one per test class, and each mutation test copies it. 103 tests now run in about 158 seconds, where 77 tests previously took about 305; no check was removed or skipped to achieve that. Round 4 brings the suite to 160 tests in about 123 seconds.
- Tests that needed a stand-in certifier now plant a real one — a single light at the centre of the square, which certifies immediately — instead of a script that prints a status and nothing else. Such a script is no longer a successful run, which is the point of the proof-output contract; the tests that used it as their positive case would otherwise have been asserting the defect.
- Both replay scripts refuse to start under `python -O` or `PYTHONOPTIMIZE`, which would disable the `assert` statements each certifier uses to re-check its own certificate, and remove `PYTHONOPTIMIZE` from the child environment.
- `.github/workflows/smoke-test.yml` also runs the unit tests, the semantic consistency check, the generator check and the upper witness audit.
- `.github/workflows/full-replay.yml` runs on `workflow_dispatch`, `workflow_call`, a weekly schedule and every push and pull request, with no `paths:` filter: a workflow skipped by a path filter reports no status, and a required check that is never reported leaves a pull request pending. The job is self-contained — unit tests, every static check, the replay and the replay-output validator — so it can be the single required check. CI output goes to a scratch directory and never overwrites `evidence/full-cleanroom-replay/`; the artifact upload warns rather than errors on an empty directory so it cannot bury the real failure.
- All `uses:` references are pinned to full 40-character commit SHAs.
- `MANIFEST_POLICY.json` includes `tests` in the integrity manifest.
- `scripts/build_release_assets.py` fixes three more release-engineering defects, each measured before it was fixed. **The environment was part of the output**: `git archive --format=zip` writes DOS member timestamps in local time, so the same commit built under `TZ=UTC` and `TZ=Pacific/Kiritimati` produced different digests, fourteen hours apart. The subprocess environment is now *constructed* from an allow-list with `TZ=UTC` and `LC_ALL=C` fixed and every repository-routing variable (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_SHALLOW_FILE`, all `GIT_CONFIG_*`) dropped, rather than filtered — a deny-list has to anticipate every variable that matters, and `TZ` is the one that got through. **Delivery was not atomic**: the ZIP, the checksum companion and the record were moved into place one at a time, so a failure on the second move left a canonical-named ZIP behind while the builder reported that nothing had been published. All three are now produced in a staging directory beside the destination and published by a single `rename` of that directory, which is why `--output-dir` must not already exist; the destination is either absent or complete. **Path checks did not cover control characters**: carriage returns, newlines, tabs and other C0/C1 characters are now rejected, as are paths where one entry is also a directory prefix of another, and archive permission bits are compared against the Git mode rather than only the executable bit. `--expect-asset-sha256` was added so a tagged build can be required to reproduce the digest of a build made *before* the tag existed, which is the only point at which a mismatch is still recoverable.
- `scripts/build_publication_attestation.py` and `tests/test_publication_attestation.py`: the dynamic publication record is now a third release **asset**, `…-v1.0.2.publication-attestation.json`, uploaded to the draft Release before publication. It was previously going to be the release body. GitHub's immutable releases protect the tag and the assets, and GitHub's documentation states that once immutable releases are enabled you can only edit the title and release notes after a release is published — so a record kept in the body would have stayed editable for the life of the release and could not be the integrity authority. The generator measures nothing itself: it reads **two** files — the facts gathered from GitHub and CI, and the machine-produced `build-record.json` written by the asset builder — and refuses unless they agree with each other and with this project's fixed history. It reads the builder's own record rather than a retyped copy, because a hand-written builder command was accepted when it was `["echo", "not-a-builder"]` and when its target was not the merge commit. It rejects duplicate keys, `NaN`, unknown or missing fields, nulls, booleans in integer fields, malformed digests and timestamps that are not real calendar dates — `2026-99-99T99:99:99Z` passed a regex-only check — and then applies the cross-field rules that actually matter: the validator counters must equal 88 rather than merely agree with each other (1/1/1 passed), both CI runs must be attempt 1 rather than any positive number, the two run ids and the two asset ids must differ, the build record's target commit and tree must be the merge commit and tree, the archive command must end in that commit, the build must have been made under `TZ=UTC`, the checksum companion is rebuilt from the ZIP digest and the asset name and compared byte for byte, the tag target must be the merge commit, the merge must have two distinct parents, the post-merge runs must have concluded `success`, the validator must report `problems=0` with a verified clean source, the ZIP digest must be identical at build, upload and re-download, the sidecar check must have passed, and the existing `v1.0.0`/`v1.0.1` assets and the audit branch must be untouched. Placeholders, credentials and absolute paths are refused outright, so an unfilled field cannot reach an asset that is about to become immutable. Output is canonical JSON, deterministic because every value comes from the input rather than from the clock, and written through a sibling temporary file and a single `os.replace`: writing straight to the destination previously left a truncated, unparseable file under the asset's name when the write failed part way through. The status it emits, `PRE_PUBLICATION_DISTRIBUTION_ASSETS_VERIFIED`, is true at the moment it is written, before this file itself is uploaded. Two facts are deliberately absent and cannot be supplied: the asset's own id and its own digest, which do not exist until it is uploaded — those, and the post-publication immutable read-back, are carried by GitHub's generated Release attestation and by the external execution evidence.
- `scripts/build_release_assets.py` gained three hardenings, each for a measured counterexample. `--require-tag` now binds to an exact `refs/tags/<name>` — `git rev-list -n 1 v1.0.2` resolves any revision, so a *branch* named `v1.0.2` previously satisfied it and produced a signed-looking build with no tag in existence. The archive is now compared file by file, byte by byte and mode by mode against the raw target tree read with `ls-tree` and a strict `cat-file --batch`, with system, global and injected attribute sources neutralised and a non-empty `.git/info/attributes` refused: an `export-ignore` line there is in no commit, does not appear in `git status`, and silently dropped a file from the archive, so two builds of one commit differed in content and digest. And the build is now transactional — everything is produced in a private staging directory and moved to the destination only after every check passes — because a failed verification previously left a canonical-named ZIP and a *valid* checksum companion behind, which a later upload step could have published. The path checker was also given one shared normaliser that rejects backslashes, drive letters, UNC prefixes, empty and dot components and duplicate entries, and rejects symlink and submodule entries by file type; a `..\` traversal and a symlink entry both passed the previous check. The public build record now carries `<REPOSITORY>` and `<OUTPUT_ZIP>` in place of local paths, since it is destined for a published attestation.
- `PUBLICATION_AUDIT.json` is now a **static release-candidate audit** rather than a publication attestation. A file cannot state the identity of the commit that contains it: the final merge commit, the post-merge CI run ids, the release artifact digest and the canonical ZIP digest all come into existence after the commit that would have to carry them, and recording a CI result in a commit changes that commit and invalidates the record. The file therefore carries only what is knowable before its own commit exists — version, candidate date, base commit, frozen anchor, the exact delta from `v1.0.1`, the manifest facts, and the local replay result labelled as local and dirty-source — and states in-file that the dynamic publication attestation is a separate release asset. `docs/release-record-v1.0.2.md` is deliberately not created.
- `PUBLICATION_STATUS.md`, `release-assets/README.md` and the status paragraph of `docs/errata-v1.0.1.md` no longer say that the release does not exist yet. Those documents ship inside the tag, so any sentence of the form "not yet published" becomes false the moment the release is published, and an immutable tag and a published Release cannot be edited afterwards to repair it. They now state a conditional rule instead — the GitHub Release is the live authority; if GitHub reports the `v1.0.2` Release published and immutable then `v1.0.2` is canonical, otherwise `v1.0.1` remains the latest canonical Release — which is true both before and after publication and needs no post-release correction. The asset digests are likewise left to the publication-attestation asset and to GitHub's Release asset metadata, because a file inside the archive cannot state that archive's digest.

- `scripts/build_release_assets.py` binds the builder that runs to the builder in the commit it archives, and stops calling a published output "nothing". Both for measured counterexamples. **The executing script was not bound to the target commit**: a target whose `scripts/build_release_assets.py` blob was different bytes from the script that actually ran produced exit 0 for the pre-tag build, exit 0 for the tagged build and exit 0 for the publication attestation. The record carried a 40-hex blob id and a 64-hex file digest, which cannot be pasted into each other's slot — a type rule, not provenance. The builder now requires `HEAD` to be the target, reads the builder blob out of the raw target tree with a strict `cat-file --batch`, hashes those bytes and the bytes of the running file, refuses before any output when they differ, and hashes the running file again before writing the record. **A tagged build could skip the pre-tag digest gate**: `--require-tag v1.0.2` with no `--expect-asset-sha256` recorded `expected_asset_sha256: null` and was accepted, so the final asset never showed that the gate had been used; `--require-tag` now requires `--expect-asset-sha256`. **After the rename there is no such thing as "nothing published"**: failing the parent-directory `fsync` that follows the publishing rename produced exit 2 and the message `nothing published` while a complete, valid three-file directory sat on disk. That state now has its own exit code — `2` is a refusal before the publication commit point and leaves no output, `3` means the output exists and is complete but its durability is unknown — and the message says so and says not to re-run or upload automatically. The record is schema `…-build.v4` and adds `head_commit`, the builder blob id and mode, the target and executed digests, the equality verdict, and the exact output inventory; `archive_command` is now derived from the argv that actually ran rather than written out a second time.

- `scripts/build_publication_attestation.py` checks the build record as a whole document and publishes it, rather than publishing a digest of a file the reader never sees. Its record schema was partial — a handful of fields required by name and everything else let through — so it accepted a record from an unbound builder, a record from a tagged build with no expected digest, and a fixture record in which `check_release.py` had never run inside the archive. Every top-level key and every key of every nested block is now named, unknown keys are refused, `1e999` is refused as a non-finite number, and the archive command must be the exact expected argv rather than merely containing `git`, `archive` and `--format=zip`. Both archive self-checks must be present and have exited 0, and `not_present_in_archive` must be empty. The strictly validated record is embedded in the asset under `canonical_assets.build_record`, with the canonicalisation stated, so `build_record_sha256` is recomputable from what is published; the record file itself must already be in that canonical spelling. `builder_script_blob_oid` is no longer a hand-supplied fact and is refused if supplied. The measured facts gained the relations that stop an answer from another release or another run being mixed in: repository full name, the draft's tag name and draft state, each CI run's workflow name, event, head branch and head SHA, the replay artifact's name, run id and expiry, and each asset's name and parent release id. The generator's own write gained the same two-state contract as the builder: exit 2 before `os.replace`, exit 3 after it, because a failing directory `fsync` after the replace previously reported `nothing published` over a complete 4,626-byte asset.

- Both generators now hold the publication commit point against a *second* failure. Exit 3 was introduced for a durability step failing after the output existed, but the code that described what existed could itself fail, and when it did the exception escaped the handler that was classifying the state: a complete three-file output directory, and a complete 9,414-byte attestation, were both reported as exit 2 with the message `nothing published` — measured. Everything after `os.rename` and after `os.replace` is now caught as `BaseException` and reclassified to exit 3, the inspection and the read-back are best-effort helpers that record their own failures instead of raising them, and the message distinguishes three states rather than two: verified complete, verified incomplete, and **existing but not verifiable**. An undetermined check is reported as unknown rather than collapsing into false, because "we could not tell" is not the same claim as "it is broken", and neither is the same claim as "it is not there".

- The publication attestation now takes the draft Release's exact asset inventory as a measured input: `draft_asset_count_before_attestation`, `draft_asset_names_before_attestation` and `draft_asset_ids_before_attestation`. The count must be 2, the names must be exactly the ZIP and its checksum companion in canonical order, the ids must be exactly the two recorded asset ids, duplicates in either list are refused, and the attestation's own name may not appear — it is uploaded afterwards, so a document that listed itself would be describing its own upload. Any other file sitting on the draft would be frozen by the same `publish` call and would never have appeared in any record; nothing checked for one.

- The publication commit point is now the `os.rename` and `os.replace` **calls**, not the statements after them. Both syscalls complete inside C, and CPython delivers a signal between bytecodes, so an interruption arriving in that window left `published = True` — and `temporary = None` — unexecuted while the output was already on disk. Measured: a `KeyboardInterrupt` and a `SystemExit` raised at that instant escaped every handler in both tools, killing the process with a traceback beside a complete three-file output directory and a complete, valid attestation. `BaseException` is not `Exception`, which is why none of the previous handlers saw them. Each syscall is now wrapped in `except BaseException`, and the classification is made by **looking at the filesystem** rather than by trusting a flag that may never have been assigned: the destination is inspected with non-throwing helpers, and only a definite "the output does not exist" permits reporting an absence — an inspection that itself fails yields unknown, and unknown is treated as published. The builder additionally records the staging directory's `(st_dev, st_ino)` before the rename and compares it with the destination afterwards, so the report can say whether the published directory is the staging directory that was moved. `main()` in both tools now catches `BaseException` so a Ctrl-C cannot leave a traceback instead of an exit code.

  This does not make the tools interruption-proof, and they do not claim to be. `SIGKILL`, a process crash and a power loss cannot be caught by any handler; what is bounded is the reporting, which will not assert that nothing was published when something may have been.

- The interruption boundary now runs from the syscall to the CLI's return, not just around the syscall. Wrapping `os.rename` and `os.replace` closed the window inside the call and left two later ones open, both measured with `KeyboardInterrupt`, `SystemExit` and a custom `BaseException` delivered by line-event injection. **The first statement after the guard** — the one that records that the syscall happened — sat outside every handler, so an interruption there produced exit 2 and `nothing published` over a complete three-file directory and over a complete attestation. **The success report**, reached after the helper had already returned, sat outside the handlers too, so an interruption there escaped as a traceback with the output on disk and nothing on stderr; an operator reading that would reasonably re-run. The publication transaction in both tools now spans the syscall, the state update, the durability `fsync` and the return, and `main()` spans the call into the builder, the success report and its own return. Failures are still classified by looking at the destination rather than by which line was executing: only a definite absence permits reporting an absence, and an unknown counts as published. `Refused` keeps a separate branch because it is raised only by preconditions, where the destination is known not to exist — so an existing `--output-dir` is still exit 2, not exit 3.

  The uncatchable boundary is unchanged and is not narrowed by this: `SIGKILL`, a process crash and a power loss cannot be caught, and no claim of interruption-proofness is made. What is bounded is the reporting.

- The evidence package now verifies the release *scope* and the candidate *date* rather than their shapes.
