# Result table schema and rounding policy

`data/certified-results.csv` and `data/certified-results.json` are **build
products**. They are generated by `scripts/regenerate_certified_results.py` and
must never be edited by hand; `--check` compares the files on disk with what the
generator produces and fails if they differ.

Both files carry the same 44 records, in the same field order, with every value
as a string. The JSON is the CSV, record for record and field for field:
`scripts/check_semantic_consistency.py` compares them as strings, never as
floats, because two 87-digit decimals that differ in the last place are the same
`float`.

## Where each field comes from

| Field | Source |
| --- | --- |
| `n` | the configuration size |
| `certified_lower_bound` | the `TARGET` literal shared by both certifiers, copied verbatim so trailing zeros survive |
| `rigorous_upper_witness` | computed — see below |
| `interval_width` | computed — see below |
| `source_count` | the number of coordinates in `data/configurations/nNN/coordinates.csv` |
| `minimum_source_separation` | descriptive metadata (see below) |
| `symmetry_or_family` | provenance prose, from `data/results-metadata.json` |
| `all_local_minima_count` | from `data/results-metadata.json` |
| `spectral_splits`, `spectral_maximum_depth`, `componentwise_splits`, `componentwise_maximum_depth` | the stored clean-room replay in `evidence/full-cleanroom-replay/` |
| `submitted_lower_bound`, `external_status`, `notes` | from `data/results-metadata.json` |
| `configuration_path`, `spectral_verifier_path`, `componentwise_verifier_path` | derived from `n` |
| `full_replay_status` | the stored clean-room replay status of both certifiers |

`data/results-metadata.json` holds only values that have no definition to
compute: provenance prose, the externally submitted figure, the local-minima
count, the descriptive minimum separation, and the presentation precision. No
derived quantity is entered there.

## `certified_lower_bound`

The certified lower bound is the value each certifier proves by exhaustive
rational branch-and-bound over the whole unit square:

    min over p in [0,1]^2 of  sum_i 1 / ||p - c_i||^2   >=   certified_lower_bound

It is an exact finite decimal, and both the spectral and the componentwise
certifier for that `n` declare the identical literal.

## `rigorous_upper_witness`

Each configuration has one **upper witness point** `p*` in `[0,1]^2`, taken from
the certifier source. Seventy-six of the 88 certifiers declare it as a named
constant (`UPPER_WITNESS`, `WITNESS_POINT` or `WITNESS`); the other twelve
declare no constant and evaluate the potential at the corner `(0, 0)` inside
`main()`, where the checking tools recover the point by evaluating the argument
expression rather than assuming the corner. Sixteen certifiers use `(0, 0)` in
total, four of them through a named constant. Evaluating the potential at `p*`
gives an exact rational number, which is by definition an upper bound for the
minimum:

    exact_witness_value = sum_i 1 / ((p*x - x_i)^2 + (p*y - y_i)^2)

`rigorous_upper_witness` is that exact value **rounded outward, that is
upward**, to the row's decimal places:

    rigorous_upper_witness = ceil(exact_witness_value * 10^d) / 10^d

The rounding is done in integer arithmetic
(`certificate_lib.round_up_to_places`): the magnitudes involved are far outside
what binary floating point can represent, and the `decimal` precision that would
be needed depends on the value. The positivity precondition is checked with an
explicit `raise`, not an `assert`, so it still holds under `python -O`.

Rounding to nearest is **not** acceptable here: whenever the first dropped digit
is below 5 it produces a decimal below the exact value, which is then not an
upper bound at all. That is what happened in v1.0.0 and v1.0.1, in 18 of the 44
rows — see [errata-v1.0.1.md](errata-v1.0.1.md).

### Decimal places

`d` is recorded per row in `data/results-metadata.json` as
`upper_decimal_places`. The values in use are those published in v1.0.1: 57, 67,
68, 78, 87 or 97 decimals, depending on the configuration family.

A single fixed width for all 44 rows was considered and rejected. The published
decimals are already correct to their stated precision for 26 of the 44 rows,
and imposing one width would rewrite every row of a released dataset in order to
fix eighteen last digits. Preserving each row's precision keeps the correction
auditable: every changed digit is a digit that was wrong.

Whatever `d` is, the rounding direction is the same for every row — always
outward. `scripts/audit_upper_witness.py` recomputes each row from the published
coordinates and reports `BELOW_EXACT`, `EQUAL_EXACT` or `ABOVE_EXACT`, and exits
non-zero if any row is `BELOW_EXACT`.

## `interval_width`

    interval_width = rigorous_upper_witness - certified_lower_bound

computed exactly, as the difference of two finite decimals, and printed with
`max(d, decimal places of the lower bound)` decimals. It is never rounded: if
the difference were not exactly representable at that width, the generator
raises instead of writing an approximation.

Because `rigorous_upper_witness` is rounded outward and
`certified_lower_bound` is exact, `interval_width` is a genuine enclosure width:
the true minimum lies in
`[certified_lower_bound, rigorous_upper_witness]`.

## Writing the two files

Each payload is completed in memory, written to a temporary file in the same
directory, flushed, fsynced and moved into place with `os.replace`, which is
atomic within a filesystem. So neither file can be left truncated or partially
written.

The **pair** is not atomic. There is no way to replace two files in one
operation here, so an interruption between them leaves the CSV new and the JSON
old. That state is not silent: `regenerate_certified_results.py --check`
compares both files against the generator, and
`check_semantic_consistency.py` compares the CSV and the JSON field by field.
Either one reports it.

## `symmetry_or_family`

**Non-normative provenance prose.** It records where a configuration came from.
No bound depends on it, no check derives anything from it, and it is carried
through the generator unchanged from `data/results-metadata.json`.

Read as an exact statement about the published decimals, two entries were wrong
in v1.0.0 and v1.0.1; see [errata-v1.0.1.md](errata-v1.0.1.md).
`certificate_lib.exact_square_symmetries` computes, in exact rational
arithmetic, which of the eight symmetries of the square fix a configuration —
that function, not this column, is where an exact symmetry claim should come
from.

## `minimum_source_separation`

A descriptive figure: the exact minimum distance between two sources of the
configuration is irrational in general, so this column holds it rounded to
nearest at the precision shown. It is not part of any bound and is not used by
any proof. `scripts/check_semantic_consistency.py` verifies that each published
value is within half a unit in the last place of the exact separation, comparing
squared distances so that no square root is ever taken approximately.

## Checking all of this

```bash
python -B scripts/regenerate_certified_results.py --check   # tables are current
python -B scripts/check_semantic_consistency.py             # all representations agree
python -B scripts/audit_upper_witness.py                    # every upper bound is exact-safe
```

All three read JSON through a strict loader that rejects duplicate object keys
and `NaN`/`Infinity`, so a document two readers would disagree about is an
error rather than a silent last-one-wins.

`-B` keeps the working tree free of `__pycache__`, which
`scripts/check_release.py` treats as a packaging defect.
